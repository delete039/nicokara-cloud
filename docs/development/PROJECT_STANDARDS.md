# 项目开发与版本标准

## 当前版本

当前代码版本为 `v4.1`，内部规范文件 `VERSION` 保存为 `4.1`。用户可见的版本标签、更新日志和 Git 标签使用 `v4.1`。

## 版本历史

功能阶段和旧版本的完整映射见 [VERSION_HISTORY.md](../releases/VERSION_HISTORY.md)。不再沿用旧的 `0.x`、`alpha`、`beta` 命名作为当前版本。

## 版本递增

- 可兼容的新功能、修复、性能优化和部署修复：递增最后一位，例如 `v4.1` → `v4.2`。
- 修改 KRL、LRC、时间轴 JSON、API 或任务状态契约，且需要迁移或不兼容旧数据：由用户确认后进入 `v5.0`。
- 单次构建不自动产生新版本；构建时间和短提交号只用于产物追踪。
- 每次发布必须同时更新 `VERSION`、前后端元数据、`CHANGELOG.md`、路线图和发布清单。

## 代码与文件边界

- `backend/`：服务端 API、任务队列、识别、对齐和渲染逻辑。
- `frontend/`：网页、预览、浏览器本地导出和公告显示。
- `docs/`：面向开发者、部署者和用户的说明。
- `release/`：发布模板、打包工具和部署脚本；生成的包归档后不得散落在工具文件旁。
- `.env`、模型、SQLite 数据库、任务文件、缓存和视频属于运行数据，不纳入源码版本。

## 公告内部格式

公告可以在内部增加 `version`、分类、排序和迁移字段，但 `AnnouncementDialog` 的用户可见内容和布局必须保持兼容。需要变更显示时，必须作为独立的用户界面任务处理，不能借版本整理顺便改变。

## 验证门槛

发布前至少执行：

1. `python release/check_version.py` 版本一致性检查；
2. 后端相关测试；
3. 前端 typecheck 和相关 Vitest 测试；
4. 前端生产构建；
5. Git 状态、发布清单和 SHA-256 校验复核。

## 提交和外部操作

提交信息使用 `feat:`、`fix:`、`refactor:`、`docs:`、`test:` 或 `chore:` 前缀。上传 GitHub、创建标签、发布资产和部署服务器属于外部状态变更，必须在任务中明确获得授权后执行。
